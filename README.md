# Модуль LLM/RAG для проверки расходов

Python-модуль принимает результаты анализа препаратов от предыдущего компонента, ищет основания в предоставленном корпусе и формирует комментарии с цитатами, статусы и резюме заявки. Исходные МНН, категории и результаты проверки дозировки сохраняются.

Поддерживаются генерация через GigaChat, локальные бесплатные эмбеддинги MiniLM и запуск без внешнего API. Сейчас используются синтетические данные; реальная интеграция с предыдущим модулем ещё не подключена. GigaChat можно проверить на готовой демонстрационной заявке через локальное меню.

## Структура проекта

```text
src/llm_rag/          Код библиотеки и командный интерфейс
  application.py     Общая функция запуска и чтение настроек .env
  contracts.py       Входные и выходные модели
  corpus.py          Модели корпуса и проверка целостности
  retrieval.py       Отбор и ранжирование источников
  vector_index.py    Векторный индекс в памяти
  embeddings.py      Локальная модель эмбеддингов
  evidence.py        Применимость оснований и конфликты
  generation.py      Подготовка контекста для генератора
  validation.py      Проверка утверждений и цитат
  summary.py         Резюме и расчёты сумм
  pipeline.py        Обработка заявки
  providers/         GigaChat, JSON-шлюз и локальное демо
tests/               Тесты
examples/            Два необходимых JSON-примера: заявка и корпус
docs/ТЗ.docx         Исходное техническое задание
run.py               Запуск из папки проекта
check_local.py       Меню для ручной локальной проверки
requirements.txt     Все внешние зависимости приложения и тестов
pyproject.toml       Метаданные пакета и настройки тестов
.local/              Локальные отчёты, архив помощника и временные результаты
```

`.local/`, `.env`, веса моделей, кэши, сборки и настройки IDE исключены из Git. Сгенерированные схемы и результаты запусков не нужны в репозитории. Тексты прежних планов и отчётов сохранены в `.local/archive/`.

## Установка и первый запуск

Python 3.11 или новее. Команды PowerShell выполняются из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py --output .local/results/demo.json
```

Все внешние зависимости приложения и тестов перечислены в одном `requirements.txt`: `pydantic`, `python-dotenv`, `gigachat`, `httpx`, `torch`, `transformers`, `huggingface-hub`, `pytest`, `jsonschema`, `requests`. Команда выше устанавливает библиотеки; проект запускается через `run.py` без отдельной установки. `pyproject.toml` читает зависимости из того же файла, а транзитивные зависимости pip устанавливает автоматически.

По умолчанию запускаются лексический поиск и `DemoProvider`: он извлекает разрешённые утверждения из тестового корпуса и не вызывает LLM. В примере восемь позиций, итог `PARTIAL` и сумма `355.00 RUB`.

## Локальная проверка через меню

```powershell
.\.venv\Scripts\python.exe check_local.py
```

Пункты 1 и 2 запускают демо без API с обычным или векторным поиском. Пункты 3 и 4 вызывают GigaChat с соответствующим способом поиска; выбор этих пунктов разрешает отправку демонстрационного контекста в API. Пункт 5 позволяет выбрать другие JSON-файлы заявки и корпуса. Пункт 6 разрешает или запрещает первоначальное скачивание модели при следующем векторном запуске; по умолчанию скачивание запрещено. Пункт 7 переключает проверку сертификата сервера только для текущей сессии меню. Пункт 0 завершает программу.

Если GigaChat выдаёт `GIGACHAT_TLS_ERROR` и нужно выполнить локальную проверку без установки сертификата, выберите 7, затем 4. Соединение останется зашифрованным, но подлинность сервера проверяться не будет. При новом запуске меню проверка снова включена. Обычный `run.py` всегда использует проверку сертификата. Для работы с проверкой используйте сертификат по [инструкции GigaChat](https://developers.sber.ru/docs/ru/gigachat/certificates) и настройку `GIGACHAT_CA_BUNDLE_FILE`.

По умолчанию используются `examples/request.json` и `examples/corpus.json`. Меню показывает статусы, комментарии, цитаты, суммы и путь к полному JSON в `.local/results/`. Каждый запуск сохраняется в отдельный файл. Пути по умолчанию определяются относительно расположения скрипта, поэтому его можно запустить из другой папки. Если у позиций возникли `PROCESSING_ERROR`, меню сообщает о технических ошибках; сохранённый файл сам по себе не подтверждает успешный вызов API.

`check_local.py` и `run.py` вызывают общую функцию `analyze_files()` из `llm_rag.application`, которая использует существующий `Pipeline.run()`. Логика анализа в меню не дублируется.

## Векторный поиск

```powershell
.\.venv\Scripts\python.exe run.py --retrieval vector --output .local/results/vector.json
```

Используется локальная модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`: русский язык, 384 измерения, CPU. На текущем компьютере веса уже есть в стандартном кэше Hugging Face. Если модель отсутствует, первоначальное скачивание разрешается явно:

```powershell
.\.venv\Scripts\python.exe run.py --retrieval vector --download-embeddings --embedding-cache .local/models --output .local/results/vector.json
```

После скачивания используйте ту же `--embedding-cache .local/models` без флага скачивания. Обработка текстов выполняется локально; ключ API для эмбеддингов не нужен. Модель обрабатывает до 128 токенов строки, индекс хранится в памяти.

Источники сначала отбираются по МНН и диагнозу. Затем учитываются явные ссылки и косинусная близость. Все подходящие фрагменты сохраняются для проверки конфликтов. В итоговом `retrieval_info` указаны метод поиска, модель, версия, размерность и отпечаток корпуса.

## GigaChat

Используется [официальный Python SDK `gigachat`](https://developers.sber.ru/docs/ru/gigachain/tools/python/gigachat), версия `0.2.0`. Адаптер вызывает `GigaChat.chat()` с моделью `Chat`; получение, хранение в памяти и обновление токенов выполняет SDK. JSON-ответ дополнительно проверяется кодом проекта по разрешённым утверждениям и цитатам. Сетевой клиент закрывается после обработки заявки; при прямом использовании `GigaChatProvider` используйте `with` или вызовите `close()`.

Схема ответа привязана к идентификатору позиции и разрешённым утверждениям: число элементов ограничено, а текст, цитата и идентификаторы выбираются только в согласованных сочетаниях. Ответ модели всё равно проходит независимую проверку проекта.

Ключ автоматически читается из `.env` в корне проекта или из переменной окружения `GIGACHAT_CREDENTIALS`. В `.env` укажите Authorization Key без префикса `Basic`:

```dotenv
GIGACHAT_CREDENTIALS=ваш_ключ
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat-2
```

Запустите меню или используйте команду:

```powershell
.\.venv\Scripts\python.exe run.py --provider gigachat --enable-api --retrieval vector --output .local/results/gigachat.json
```

Для проекта организации укажите его scope: `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP`. Модель задаётся доступным вашему проекту идентификатором. Вместо Authorization Key можно передать временный `GIGACHAT_ACCESS_TOKEN`; обе переменные одновременно не допускаются. При необходимости собственного доверенного CA bundle задайте `GIGACHAT_CA_BUNDLE_FILE`. Проверка TLS включена по умолчанию; временное отключение предусмотрено пунктом 7 локального меню.

`.env` исключён из Git. Настройки читаются заново при каждом анализе; уже заданные переменные окружения имеют приоритет над файлом. Для другого файла настроек в CLI используйте `--env-file путь`. Секреты не выводятся в меню и не записываются в результат. В CLI API включается флагом `--enable-api`; в меню — выбором пункта GigaChat. Ключ из `.env` не делает обращения к API автоматическими.

Альтернативный провайдер `--provider gateway` отправляет наш внутренний контекст POST-запросом на HTTPS `--endpoint` с `LLM_RAG_API_KEY` в Bearer-заголовке. Он ожидает ответ `{item_id, claims}`, где каждое утверждение содержит `claim_id`, `text`, `fragment_id`, `quote`. Этот протокол не является универсальным API поставщиков.

## Вход и результат

Рабочие примеры: [заявка](examples/request.json) и [корпус](examples/corpus.json). Для собственных файлов:

```powershell
.\.venv\Scripts\python.exe run.py --request examples/request.json --corpus examples/corpus.json --output .local/results/result.json
```

Контракт заявки версии `1.0` включает `request_id`, `diagnosis`, `items`, `is_demo=true` и необязательный словарь `context`. Суммы передаются десятичными строками, категории — кириллическими `А`, `Б`, `В` либо `null`. `dosage_check.status`: `VALID`, `INVALID`, `INSUFFICIENT_DATA`, `NOT_CHECKED`. `upstream_status`: `PROCESSED`, `PARTIAL`, `FAILED`. Окончательные поля ещё предстоит согласовать с предыдущим модулем.

Статусы объяснения: `SUPPORTED`, `INSUFFICIENT_DATA`, `UNCONFIRMED`, `SOURCE_CONFLICT`, `PROCESSING_ERROR`. Результат содержит проверенные утверждения и цитаты, причины, недостающие сведения, ссылки резюме и нерешённые позиции. Полнота: `COMPLETE`, `PARTIAL`, `UNRESOLVED`. При `NOT_CHECKED` подтверждение относится только к категории, а не к дозе или лечению.

Медицинский текст допускается только в точной разрешённой формулировке, размеченной в корпусе. Наличие цитаты само по себе не разрешает другой вывод. Условия не угадываются; категория №2 при конфликте сохраняется. Суммы считаются через `Decimal` по каждой валюте, без повторного умножения на количество. Процент компенсации не рассчитывается. Исходные PDF/Word автоматически в корпус не преобразуются; качество на реальных медицинских данных не подтверждено.

JSON-схемы при необходимости создаются из моделей, а не хранятся в ветке:

```powershell
.\.venv\Scripts\python.exe run.py --export-schemas .local/schemas
```

Код возврата CLI `0` означает, что результат заявки сформирован: отдельные позиции могут требовать проверки или содержать `PROCESSING_ERROR`. Код `2` означает ошибку входа, настройки или файлов.

При известной ошибке GigaChat поле `reasons` содержит безопасный код причины, который меню поясняет по-русски: например, `GIGACHAT_TLS_ERROR`, `GIGACHAT_AUTH_FAILED`, `GIGACHAT_FORBIDDEN` или `GIGACHAT_TIMEOUT`. Произвольные сообщения исключений, заголовки и тела ответов API в результат не включаются.

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Кэш и временные файлы тестов размещаются в `.local/`. Реальная модель проверяется отдельно при наличии весов:

```powershell
$env:LLM_RAG_TEST_LOCAL_EMBEDDINGS = '1'
.\.venv\Scripts\python.exe -m pytest -q
Remove-Item Env:LLM_RAG_TEST_LOCAL_EMBEDDINGS
```

Для встраивания в другой компонент можно отдельно установить сам пакет командой `python -m pip install .` и использовать `Pipeline(corpus, provider, embedder=...)` из `llm_rag.pipeline`. Вход проверяется через `AnalysisRequest` из `llm_rag.contracts`, выход — `AnalysisResult`. Парсинг Excel, классификация, интерфейс комиссии и окончательное решение врача находятся за пределами этого пакета.
