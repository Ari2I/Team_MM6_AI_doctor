# Backend ИИ-ассистента «Врач»

Backend для секретаря комиссии по трудным жизненным ситуациям: принимает Excel-заявку,
проверяет пары «препарат + диагноз» по справочнику, формирует светофор и отчёт Excel.
Результат рекомендательный, решение принимает человек.
Справочник демонстрационный и синтетический: это не клинические рекомендации.

## 1. Что нужно установить

- Docker Desktop с запущенным движком Linux-контейнеров и командой `docker compose` (Compose v2).
- Git для Windows; все команды ниже выполняются в **Git Bash** из корня репозитория.
- Доступ к интернету при первой сборке: Docker скачает образы и Python-зависимости.

Python на Windows **не нужен**: Dockerfile использует `python:3.11-slim`, устанавливает
зависимости вместе с pytest и ruff. База — `postgres:16-alpine`.
Проверка инструментов:

```bash
git --version
docker version
docker compose version
curl --version
```

Ожидается вывод версий; у `docker version` доступны Client и Server.
`curl` используется из Git Bash. Отдельные минимальные версии Git/Docker в проекте не зафиксированы.

## 2. Быстрый старт с нуля

1. Клонируйте репозиторий и перейдите в него:

   ```bash
   git clone https://github.com/Ari2I/Team_MM6_AI_doctor.git
   cd Team_MM6_AI_doctor
   ```

   Ожидается наличие `docker-compose.yml`, `Dockerfile`, `.env.example`, `app/`, `tests/`.
   Все следующие команды запускайте из этой папки.

2. Создайте локальные настройки:

   ```bash
   cp .env.example .env
   notepad.exe .env
   ```

   Измените `POSTGRES_PASSWORD` на свой локальный пароль и сохраните файл.
   Для простоты используйте буквы и цифры без пробелов и `$`, чтобы избежать интерполяции Compose.
   Не копируйте пароль в README, чат или Git.

   | Переменная из `.env.example` | Что делать |
   | --- | --- |
   | `POSTGRES_DB=vrach` | Оставить: имя новой БД. |
   | `POSTGRES_USER=vrach` | Оставить: пользователь новой БД. |
   | `POSTGRES_PASSWORD` | Обязательно заменить пример своим паролем. |
   | `POSTGRES_HOST=localhost` | Оставить: Compose переопределит на `db` для API. |
   | `POSTGRES_PORT=5432` | Оставить: Compose переопределит на `5432` внутри сети контейнеров. |
   | `API_PORT=8000` | Оставить, если порт свободен. При изменении используйте новый порт во всех адресах ниже. |
   | `MAX_EXCEL_SIZE_BYTES=10485760` | Необязательная закомментированная настройка: лимит XLSX 10 МБ. Для старта не менять. |

   Ожидается файл `.env`, исключённый из Git. Настройки БД применяются при создании
   пустого тома; смена пароля в `.env` не меняет пароль уже созданной БД.

3. Соберите и запустите сервисы:

   ```bash
   docker compose up --build -d
   docker compose ps
   ```

   Ожидаются `api` и `db` со статусом `Up`, затем `healthy`. Если ещё `starting`,
   повторите `docker compose ps`. Альтернатива с ожиданием готовности:
   `docker compose up --build -d --wait`.
   API опубликован только на `127.0.0.1:8000`; БД доступна внутри Docker на `db:5432`,
   её порт на Windows **не публикуется**. Healthcheck API пока не проверяет таблицы БД.

4. Создайте таблицы существующими миграциями:

   ```bash
   docker compose exec -T api alembic upgrade head
   docker compose exec -T api alembic current
   ```

   Ожидается ревизия `e5f6g7h8i9j0 (head)`. Повторный `upgrade head` безопасен.
   Миграции автоматически при запуске API не выполняются.

5. Импортируйте демо-справочник и сделайте его активным:

   ```bash
   docker compose exec -T api python -m app.scripts.import_reference data/reference/demo.json --activate
   ```

   Ожидается: версия `demo-api-1`, диагнозов 3, препаратов 6, правил 6, `активна=True`.
   Это действие выполняется один раз для новой БД. Повтор той же версии — ошибка
   «уже импортирована»; без `--activate` импорт создаёт неактивную версию.

6. Откройте Swagger: <http://127.0.0.1:8000/docs>.
   Выберите `GET /health` → **Try it out** → **Execute**. Или выполните:

   ```bash
   curl --fail-with-body --silent --show-error http://127.0.0.1:8000/health
   ```

   Ожидается HTTP 200:

   ```json
   {"status":"ok","disclaimer":"Анализ носит рекомендательный характер. Решение принимает человек."}
   ```

   Это проверка процесса API без обращения к БД. Полную проверку выполняет загрузка заявки ниже.

## 3. Проверка вручную

### Через Swagger

1. В `POST /applications` нажмите **Try it out**, в поле `file` выберите
   `tests/data/sample_ok.xlsx`, поле `diagnoses` оставьте незаполненным и нажмите **Execute**.
2. Ожидается HTTP 201, `application.status=analyzed`, 6 элементов `items`,
   6 проверок в `items[].checks` и предупреждение `multiple_diagnoses`.
   На исходном `demo-api-1` индикатор красный: доля А около 76,78%.
   Сохраните `application.id` из ответа.
3. В `GET /applications/{application_id}` вставьте этот UUID: HTTP 200, сохранённая карточка.
4. В `GET /applications` задайте `limit=20`, `offset=0`: HTTP 200, список от новых к старым.
5. В `GET /applications/{application_id}/report.xlsx` вставьте UUID: HTTP 200,
   скачайте файл через ссылку **Download file**.

201 означает создание заявки, поэтому дополнительно проверяйте `application.status`:
при сбое анализа он может быть `error`. Для такой заявки отчёт возвращает 409.
Несуществующий UUID даёт 404, неправильный формат UUID — 422.

### Через curl в Git Bash

```bash
BASE_URL=http://127.0.0.1:8000
curl --fail-with-body --silent --show-error \
  -F 'file=@tests/data/sample_ok.xlsx' \
  "$BASE_URL/applications" -o /tmp/vrach-card.json
cat /tmp/vrach-card.json
```

Ожидается JSON карточки с `status=analyzed`. Получите UUID без установки Python на Windows:

```bash
APPLICATION_ID=$(docker compose exec -T api python -c \
  'import json,sys; print(json.load(sys.stdin)["application"]["id"])' < /tmp/vrach-card.json)
APPLICATION_ID=$(printf '%s' "$APPLICATION_ID" | tr -d '\r\n')
printf '%s\n' "$APPLICATION_ID"

curl --fail-with-body --silent --show-error "$BASE_URL/applications/$APPLICATION_ID"
curl --fail-with-body --silent --show-error "$BASE_URL/applications?limit=20&offset=0"
REPORT_PATH=$(mktemp -t vrach-report.XXXXXX.xlsx)
curl --fail-with-body --silent --show-error \
  -D /tmp/vrach-report.headers \
  -o "$REPORT_PATH" "$BASE_URL/applications/$APPLICATION_ID/report.xlsx"
cat /tmp/vrach-report.headers
cygpath -w "$REPORT_PATH"
```

Ожидается HTTP 200, `Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`
и `Content-Disposition: attachment; filename="application-<UUID>.xlsx"`.
Последняя команда показывает Windows-путь к скачанному Excel: откройте его в табличном редакторе.
`mktemp` выбирает новое имя для каждого отчёта, чтобы не перезаписывать открытый файл.
`/tmp` здесь — временная папка Git Bash на Windows.

POST принимает также повторяемое multipart-поле `diagnoses`:

```bash
curl --fail-with-body --silent --show-error \
  -F 'file=@tests/data/sample_ok.xlsx' \
  -F 'diagnoses=Учебный диагноз 01' \
  -F 'diagnoses=Учебный диагноз 02' \
  "$BASE_URL/applications"
```

Диагнозы формы объединяются с диагнозами файла, а не заменяют их. У `sample_ok.xlsx`
уже три диагноза. Чтобы проверить ровно два диагноза, в копии файла удалите столбец
диагноза и передайте два поля формы: будет по две проверки на каждый препарат.
Не изменяйте исходные тестовые файлы.

### Реальные файлы `tests/data/`

Результаты ниже относятся к активному исходному `demo-api-1` и настройкам по умолчанию.
HTTP 201 с предупреждениями — допустимый результат, критические ошибки дают 422 и заявку не сохраняют.

| Файл | Содержимое и ожидаемый результат POST |
| --- | --- |
| `sample_ok.xlsx` | 6 препаратов, три диагноза, корректные числа; 201, `analyzed`, предупреждение о нескольких диагнозах. |
| `sample_messy_headers.xlsx` | Те же данные с пробелами, переносами и разным регистром заголовков; результат как у `sample_ok`. Это не опечатка названия препарата. |
| `sample_missing_column.xlsx` | Нет столбца «Сумма»; 422, `missing_column`. |
| `sample_bad_types.xlsx` | Текст «не число» в сумме D2; 201 с `invalid_number`, сумма этой строки исключена из долей. |
| `sample_empty.xlsx` | Только заголовки; 422, в том числе `no_data`. |
| `sample_corrupt.xlsx` | Текст под расширением XLSX; 422, `invalid_excel`. |
| `sample_parser_layout.xlsx` | Заголовки в строке 10, пустые строки, валюта, неизвестный столбец, некорректные суммы, диагноз `NA`; 201 с предупреждениями и проверками, требующими человека. |
| `sample_parser_duplicates.xlsx` | Два столбца «Сумма», используется первый. Без диагноза — 422, `no_diagnosis`; с диагнозом в форме — 201 с предупреждением о столбцах и ручной проверкой. |
| `sample_parser_no_headers.xlsx` | Нет известных заголовков; 422. |
| `sample_parser_late_header.xlsx` | Заголовки в строке 11, вне поиска; 422. |
| `sample_parser_blank.xlsx` | Пустой первый лист; 422. |
| `sample_parser_no_sheets.xlsx` | В книге удалены листы; 422, `invalid_excel`. |

Отдельных готовых XLSX с опечаткой в названии, неизвестным препаратом и ровно двумя
диагнозами нет. Неизвестные учебные названия есть в `sample_parser_layout.xlsx`;
для изолированного сценария измените название в собственной копии `sample_ok.xlsx`.
При опечатке возможны автоматическое нечёткое сопоставление или ручная проверка:
это зависит от порогов, однозначности и уверенности. Неизвестный препарат требует проверки.

`generate_samples.py` создаёт заново первые шесть файлов;
`generate_parser_samples.py` — шесть `sample_parser_*`. Скрипты перезаписывают
соответствующие вымышленные примеры. Старые пояснения в `tests/data/README.md`
о том, что валидатор не реализован, устарели; ориентируйтесь на таблицу выше и текущие тесты.

## 4. Что в отчёте Excel

| Лист | Содержимое |
| --- | --- |
| «Сводка» | Имя файла, дата создания в UTC, диагнозы, цвет светофора, доли А/Б/В/не определена, резюме, предупреждение при наличии, версии справочника, демонстрационная пометка и дисклеймер. |
| «Препараты» | Строка на каждую сохранённую пару «препарат + диагноз»: исходный номер строки, название, МНН, диагноз, категория, статус, русская причина, источник, версия и комментарий. Требующие проверки строки светло-жёлтые. |
| «Предупреждения» | Замечания валидатора: уровень, сообщение, строка и столбец. |

Заголовки выделены, шапки закреплены, длинный текст переносится;
у «Препаратов» есть автофильтр. `undetermined` отображается серым.
Экспорт форматирует сохранённую карточку и не запускает анализ заново.

## 5. Тесты и линтер в контейнере

Тестовые XLSX из `tests/data/` копируются в образ вместе с тестами:

```bash
docker compose exec -T api pytest -q
docker compose exec -T api ruff check .
docker compose exec -T api ruff format --check .
```

Ожидается успешное завершение; без `RUN_POSTGRES_TESTS=1` тесты PostgreSQL пропускаются.
Исходники не смонтированы: после изменения кода сначала пересоберите образ.
При необходимости восстановить примеры внутри контейнера можно выполнить
`docker compose exec -T api python tests/data/generate_samples.py` и
`docker compose exec -T api python tests/data/generate_parser_samples.py`.
Это не изменяет XLSX на Windows.

Полный набор требует **чистую** БД: существующий smoke-тест считает все записи `item_checks`.
Запускайте его в отдельном проекте `vrach_tests`, чтобы не затронуть заявки основного стека:

```bash
docker compose -p vrach_tests up -d --wait db
docker compose -p vrach_tests build api
docker compose -p vrach_tests run --rm --no-deps api alembic upgrade head
docker compose -p vrach_tests run --rm --no-deps -e RUN_POSTGRES_TESTS=1 api pytest -q
docker compose -p vrach_tests down -v
```

Не загружайте ручные заявки в эту БД перед тестами. Справочник импортируют сами тесты
в транзакциях с откатом. Последняя команда удаляет только тестовое окружение и его том.

## 6. Структура проекта

```text
app/

  config.py               настройки БД, пороги, метки, цвета, дисклеймер
  column_synonyms.py      синонимы заголовков и глубина поиска
  api/                    health, загрузка, карточки, список и отчёты
  schemas/                Pydantic-контракты API, парсера, проверок
  models/                 SQLAlchemy-модели заявок, парных проверок и справочника
  db/                     база моделей, движок и сессии PostgreSQL
  services/               парсер, валидатор, сопоставление, правила, расчёты, тексты, отчёт
  scripts/                импорт JSON-справочника
alembic/                  миграции схемы БД
  versions/               пять существующих ревизий
data/reference/           демонстрационный demo.json
tests/                    pytest, включая интеграционные проверки PostgreSQL
  data/                   12 вымышленных XLSX, генераторы и описание
Dockerfile                Python 3.11, зависимости, запуск uvicorn на 8000
docker-compose.yml        api, db, закрытая сеть и том postgres_data
.env.example              пример локальных настроек
pyproject.toml            зависимости, pytest и ruff
```

## 7. Ежедневная работа

Остановить без удаления контейнеров и данных:

```bash
docker compose stop
```

Запустить снова и проверить:

```bash
docker compose up -d
docker compose ps
```

Посмотреть логи (Ctrl+C завершает просмотр):

```bash
docker compose logs --tail=100 api db
docker compose logs -f api
```

После изменений Python-кода или зависимостей:

```bash
docker compose up --build -d --wait
docker compose ps
```

Пересборка сохраняет БД. Если изменились модели, схему меняют только миграцией Alembic;
после появления новой миграции выполните `docker compose exec -T api alembic upgrade head`.
Не создавайте новую ревизию для обычного запуска проекта.

**Полный сброс удаляет все заявки и справочник текущего Compose-проекта:**

```bash
docker compose down -v
docker compose up --build -d --wait
docker compose exec -T api alembic upgrade head
docker compose exec -T api python -m app.scripts.import_reference data/reference/demo.json --activate
```

Используйте только когда намеренно готовы потерять локальные данные.
Обычный `docker compose down` удаляет контейнеры/сеть, но сохраняет именованный том.

## 8. Допущения и ограничения

### Анализ и настройки

- Категории А/Б/В, их соответствие предметным правилам и названия ждут подтверждения
  заказчика/аналитика. В API используются латинские `A/B/V`; метки `CATEGORY_LABELS`:
  «Жизненно необходимые», «Сопутствующая терапия», «Сомнительные/опциональные».
- Основная логика уже реализована детерминированными правилами и справочником.
  Прежнее описание `analysis` и `traffic_light` как пустых заглушек устарело;
  правила остаются демонстрационными, не подтверждёнными клиническими правилами.
- Доли и суммы считает код. Для нескольких диагнозов категория строки выбирается
  по приоритету А > Б > В, противоречивые категории требуют проверки человеком.
  Неизвестные и неоднозначные случаи возвращаются на проверку, без придуманного обоснования.
- Дозировка, количество и длительность не оцениваются. Дозировка и количество читаются
  и сохраняются; отдельного поля длительности в текущем API/модели нет.
- Светофор допускает `green/yellow/red/undetermined`. Условие зелёного — доля А строго
  больше 80% и отсутствие проверок, требующих человека. Остальные правила ждут подтверждения.
  Текущие демонстрационные значения: порог А 80%, неопределённой доли 50%.
- Пороги находятся в `app/config.py` (`TrafficLightSettings`, `MatchingSettings`),
  синонимы заголовков — в `app/column_synonyms.py`; TODO аналитика сохраняются.
  При необходимости можно добавить в `.env` настройки из этих классов:
  `GREEN_CATEGORY_A_THRESHOLD`, `UNDETERMINED_SHARE_THRESHOLD`,
  `DRUG_AUTO_ACCEPT_THRESHOLD`, `DRUG_CANDIDATE_THRESHOLD`,
  `DIAGNOSIS_AUTO_ACCEPT_THRESHOLD`, `DIAGNOSIS_CANDIDATE_THRESHOLD`.
  Пороги нечёткого поиска по умолчанию 92/75 (шкала 0–100) для препаратов и диагнозов.
  После изменения `.env` пересоздайте сервис через `docker compose up -d`.
- LLM подключается только через `LLMProvider`; по умолчанию `provider=template`,
  внешних вызовов нет. Реальный LLM-адаптер пока не реализован; неизвестное имя провайдера
  также возвращает шаблонный провайдер. API-ключи для быстрого старта не нужны.
- Рекомендация не является решением секретаря. Анализ выставляет технический статус
  обработки (`parsed/analyzed/error`), но не принимает решение комиссии.
  Упомянутого в старом README поля `secretary_decision` в актуальной схеме нет:
  его удаляет миграция `a1b2c3d4e5f6`. Хранение решения человека пока не реализовано.

### Данные, API и парсер

- Стек: Python 3.11 в Docker, PostgreSQL 16, синхронный SQLAlchemy и psycopg 3.
  Диапазоны зависимостей заданы в `pyproject.toml`, lock-файла нет.
  Для необязательного запуска без Docker нужен собственный Python 3.11 и PostgreSQL;
  опубликованного порта БД в текущем Compose нет.
- `GET /health` возвращает `status=ok` и дисклеймер, без проверки БД.
  Дисклеймер включён даже в технический ответ по требованию AGENTS.md.
- Загружается только XLSX, лимит по умолчанию 10 МБ (`MAX_EXCEL_SIZE_BYTES`).
  Обязательны столбцы названия и суммы, хотя отдельные значения могут отсутствовать
  с предупреждениями; диагноз нужен в файле или форме. Критические ошибки запрещают
  сохранение, предупреждения — нет. Несколько диагнозов дают одно предупреждение.
- Ошибки: `{"errors": [{"level", "code", "message", "row", "column"}]}`;
  это формат AGENTS.md с оболочкой `errors` и уровнем. Сообщения на русском.
- Читается только первый лист. В первых 10 строках выбирается максимум разных
  распознанных заголовков, при равенстве — первая строка. Одного совпадения достаточно;
  без совпадений парсер возвращает `HEADER_NOT_FOUND` и отсутствующие поля.
- `column_mapping` связывает исходный заголовок с каноническим полем;
  исходное написание сохраняется, неизвестные непустые заголовки попадают в
  `unknown_columns`, пустые игнорируются. Повтор столбца: используется первый слева,
  остальные дают `DUPLICATE_COLUMN`. `missing_columns` перечисляет отсутствующие поля.
- Обрабатываются все непустые строки, включая строки с данными только в неизвестных
  столбцах. Исходный номер строки сохраняется (с 1); `column` — каноническое поле,
  для проблемы всего листа `row/column` равны `null`.
- Числа парсер читает в Decimal без проверки знака или целочисленности;
  запятая или точка — десятичный разделитель, пробелы убираются, символ валюты
  допустим с краю, `руб.`/`руб` — после числа. Одновременные точка и запятая
  дают `INVALID_NUMBER`. Денежные суммы API сериализует строками.
- Пустые/пробельные ячейки становятся `None`, нераспознанные числа — `None`
  с замечанием. `NA` и `NULL` не означают пустую ячейку. Положительные суммы участвуют
  в долях, отсутствующие, нечисловые и неположительные исключаются валидатором/агрегацией.
- Битая книга, другой формат и отсутствие листов вызывают `ExcelParseError`;
  API возвращает русскую ошибку без внутренних подробностей.
- Диагнозы объединяются по `strip().casefold()`, сохраняется первое написание.
  Диагноз строки необязателен: без него проверяются все диагнозы заявки.
  Результаты пар хранятся в `item_checks`. Диагноз строки — текстовое поле,
  без составного внешнего ключа к диагнозу той же заявки.
- UUID генерируются приложением (`uuid4`), расширения PostgreSQL не требуются.
  Начальный статус `uploaded`, `needs_review=false`; результаты до анализа пустые.
  `drug_name/dosage/quantity/amount` допускают NULL; `quantity` — NUMERIC без
  заданной точности/масштаба, `amount` — NUMERIC(12,2). Уровни в БД —
  `critical/warning`, коды замечаний — текст.
- Удаление заявки каскадно удаляет её диагнозы, препараты, проверки и замечания.
  Удаление диагноза удаляет его `item_checks`; старое описание `SET NULL` у препарата
  не соответствует актуальной схеме. Время хранится с часовым поясом;
  `created_at/updated_at` заполняет БД, `updated_at` меняет SQLAlchemy при UPDATE,
  отдельного SQL-триггера нет.
- URL подключения собирает `get_settings().database_url`, не `alembic.ini`.
  Миграция `d4e5f6g7h8i9` добавляет текстовый диагноз только там, где его ещё нет:
  предыдущая ревизия менялась после применения к части БД.

### Справочник и экспорт

- `data/reference/demo.json` — синтетические данные: существующие торговые названия,
  учебные диагнозы, демонстрационные МНН/правила. Это не клинический справочник.
  Примеры дозировок, положительных целых количеств и сумм — соглашение тестовых данных,
  а не новые медицинские правила.
- Импорт атомарен. Повтор версии запрещён; активация сериализуется блокировкой таблицы
  и защищена уникальным индексом. `name/description/is_synthetic` необязательны во входном
  JSON, `is_synthetic` допускает только `true`; метаданные дополняются демонстрационной пометкой.
  `normalized_*` заполняются через `normalize_text`, дубликаты и ссылки проверяются до записи.
  Неполные правила без категории/источника должен проверять человек.
  Миграция метаданных считает старые версии синтетическими без повторного импорта.
- Экспорт принимает сохранённую карточку (`ApplicationCard` или JSON-словарь).
  Дата — `created_at` в UTC, ISO-формат с `+00:00`; доли уже в процентах 0–100,
  отсутствующие значения пустые. Версии берутся из проверок, а не текущей активной версии.
- В карточке нет `is_synthetic`: демонстрационная пометка опирается на ограничение
  импортёра `Literal[True]` и AGENTS.md. Для несинтетических версий потребуется
  согласованное расширение метаданных карточки.
- Препарат без проверок всё равно выводится строкой «Требует проверки» без
  выдуманного диагноза/источника/версии. Неизвестная причина — «Причина требует уточнения».
  Ширина столбцов ограничена 70 символами, длинный текст переносится.
  Текст, начинающийся с `=`, `+`, `-`, `@`, экранируется апострофом от Excel-формул.
- `.env` и локальный пример пароля предназначены только для разработки.
  `.env` исключён из Git и сборки; БД хранится в именованном томе `postgres_data`.

## 9. Частые проблемы

| Симптом | Причина | Решение |
| --- | --- | --- |
| `failed to connect`, ошибка Docker pipe, недоступен Server у `docker version` | Docker Desktop не запущен или не готов | Запустить Docker Desktop, дождаться Linux-движка, повторить `docker version`. |
| Порт 8000 занят / `port is already allocated` | Уже запущен другой API | Остановить другой стек либо изменить `API_PORT` в `.env` и выполнить `docker compose up -d`; во всех URL заменить порт. |
| Подозрение на конфликт 5432 | В текущем Compose 5432 не опубликован на Windows | Локальная БД на 5432 этому стеку не мешает. Не меняйте внутренний `POSTGRES_PORT`; проверьте, не добавляли ли собственный `ports` у `db`. |
| `No module named ...`, в API нет нового маршрута | Контейнер использует старый образ/зависимости | `docker compose up --build -d --wait`; убедиться, что команда выполняется из корня этого репозитория. |
| `relation ... does not exist`, ошибка обращения к таблице | Миграции не применены | `docker compose exec -T api alembic upgrade head`, затем `alembic current` той же командой exec. |
| POST вернул 201, но `status=error`; отчёт — 409 | В том числе нет активного справочника | На новой БД выполнить импорт с `--activate` из быстрого старта, затем загрузить заявку заново. Успешный импорт должен писать `активна=True`. |
| Импорт сообщает «уже импортирована» | Версия `demo-api-1` уже есть | Не импортировать повторно. Если прежде импортировали без `--activate`, отдельной команды активации существующей версии нет; для одноразовой демо-БД допустим полный сброс из раздела 7 с потерей данных. |
| БД не принимает новый пароль | `.env` изменён после создания тома | Вернуть прежний локальный пароль; для ненужной демо-БД возможен полный сброс. Не удалять рабочий том ради проверки. |
| pytest сообщает `FileNotFoundError` для XLSX | Изменён/неполон каталог тестовых примеров или используется старый образ | Проверить `tests/data/`, пересобрать образ; при необходимости выполнить оба генератора из раздела 5. |
| curl получил HTTP 200, но завершился ошибкой записи файла | Выходной файл недоступен для записи, например открыт в Excel | Скачивать под новым именем через `REPORT_PATH=$(mktemp -t vrach-report.XXXXXX.xlsx)`, как в разделе 3. |
| Smoke-тест БД ожидает 4 проверки, но находит больше | Тест запущен на БД с ручными заявками | Использовать отдельный чистый проект `vrach_tests` из раздела 5. |
| `bash: ...\r`, `bad interpreter` после добавления shell-скрипта | CRLF в исполняемом `.sh` | В текущем репозитории `.sh` нет и запуск от них не зависит. Если добавите такой скрипт, сохраните его с LF; готовый скрипт исправления проект не содержит. |

## 10. Безопасность данных

- Содержимое заявок и ячеек в логи не записывается; API логирует только UUID,
  технический статус и время обработки. Не добавляйте названия, диагнозы и тела запросов в логи.
- `.env` и ключи не коммитятся и не выводятся в логи/промпты. Действующие ключи проекту
  по умолчанию не нужны. `.gitignore` исключает заявки XLSX/XLS вне `tests/data/`.
- В тестах и демо используются только вымышленные данные, без реальных заявителей.
- Внешний LLM выключен. При будущем подключении через `LLMProvider` допустим только
  деперсонифицированный минимум: препарат/МНН и диагноз; файлы заявок отправлять нельзя.
- Авторизации в текущем API нет. Compose публикует его только на loopback Windows;
  это окружение для локальной работы команды и демонстрации.
