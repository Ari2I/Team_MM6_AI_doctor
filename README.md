# Backend ассистента «Врач»

Каркас FastAPI-приложения на Python 3.11. Анализ носит рекомендательный характер;
решение принимает человек. Реализованы парсер Excel, валидация входных данных и схема БД;
медицинский анализ и интеграции AI/ML пока не реализованы.

## Структура

```text
app/
  main.py, config.py
  api/          HTTP-роутеры (пока только health)
  schemas/      Pydantic-схемы API
  models/       заявки, диагнозы, строки, замечания валидации и enum
  services/     excel_parser, validator; заглушки analysis, traffic_light
  column_synonyms.py  настройки распознавания заголовков Excel
  db/           декларативная база, движок и фабрика сессий
tests/
  data/         место только для вымышленных Excel-данных
  test_health.py
alembic/
  env.py, script.py.mako, versions/
```

## Запуск в Docker

Нужен Docker с Compose. Создайте `.env` из `.env.example` и задайте свой пароль.
В PowerShell:

```powershell
Copy-Item .env.example .env
docker compose up --build
```

В Linux/macOS вместо `Copy-Item` используйте `cp .env.example .env`.
API: <http://localhost:8000>, Swagger: <http://localhost:8000/docs>.
Порт API задаётся через `API_PORT` в `.env`.
Compose ожидает готовности PostgreSQL перед запуском API; оба сервиса имеют healthcheck.
Для запуска в фоне с ожиданием готовности:

```sh
docker compose up --build -d --wait
docker compose ps
curl http://localhost:8000/health
```

Остановка без удаления данных PostgreSQL:

```sh
docker compose down
```

## Проверки в контейнере (Python 3.11)

Образ для разработки включает pytest и ruff. После сборки образа проверки можно
выполнять и без запущенной БД:

```sh
docker compose run --rm --no-deps api pytest -q
docker compose run --rm --no-deps api ruff check .
docker compose run --rm --no-deps api ruff format --check .
```

Исходники копируются при сборке: после изменений перед контейнерными проверками
выполните `docker compose build api`.

## Локальная разработка

Нужен Python 3.11. Создайте окружение и установите зависимости:

```sh
python -m venv .venv
```

Активируйте его через `.venv\Scripts\Activate.ps1` в PowerShell
или `source .venv/bin/activate` в Linux/macOS, затем:

```sh
python -m pip install -e ".[dev]"
pytest -q
ruff check .
ruff format --check .
uvicorn app.main:app --reload
```

Тест `/health` не требует `.env` и PostgreSQL. Для обращения к БД нужны настройки
из `.env`; в Compose хост автоматически заменяется на `db`, порт — на `5432`.
Порт PostgreSQL на хост не публикуется. Для локального Python подключите собственный
PostgreSQL и укажите его адрес в `.env`.

## Alembic

Общий источник URL подключения — `get_settings().database_url` в `app/config.py`;
он собирается из `POSTGRES_*`. Пароль не хранится в `alembic.ini`.
Alembic импортирует `app.models`, регистрируя все четыре таблицы в `Base.metadata`.
Миграции не применяются автоматически при запуске API.

```sh
docker compose exec api alembic upgrade head
docker compose exec api alembic current
```

После добавления моделей экспортируйте их из `app/models/__init__.py`, затем создайте ревизию
локально, чтобы файл сохранился в репозитории:

```sh
alembic revision --autogenerate -m "msg"
alembic upgrade head
```

Локальные команды требуют доступной БД с настройками из `.env`.

Первая миграция создаёт `applications`, `application_diagnoses`, `application_items`
и `validation_issues`, PostgreSQL enum и индексы внешних ключей.
`alembic downgrade base` удаляет эти таблицы и enum; применять только к тестовой БД
или при намеренном откате с удалением данных.

Smoke-тест требует реальный PostgreSQL с применёнными миграциями:

```sh
docker compose up -d --wait db
docker compose build api
docker compose run --rm --no-deps api alembic upgrade head
docker compose run --rm --no-deps -e RUN_POSTGRES_TESTS=1 api pytest -q
```

Без `RUN_POSTGRES_TESTS=1` только PostgreSQL smoke-тест пропускается.
Тест использует транзакцию и savepoint, изменения откатываются; таблицы создаёт Alembic.
Для изолированной проверки добавьте `-p vrach-schema-check` после `docker compose`
ко всем командам — будут использованы отдельные сеть и том PostgreSQL.

Соглашения схемы БД:

- Все первичные ключи — UUID, генерируются приложением (`uuid4`), расширения PostgreSQL не нужны.
- Начальный статус — `uploaded`, `needs_review` — `false`; оба имеют defaults в БД.
  Изменение результата анализа само по себе не меняет статус заявки.
- `drug_name`, `dosage`, `quantity`, `amount` допускают NULL, чтобы хранить результат
  парсера с предупреждениями. `quantity` — NUMERIC без заданной точности/масштаба,
  `amount` — NUMERIC(12,2). Пустые поля анализа — NULL до анализа.
- Категории хранятся латинскими `A / B / V`: русские А / Б / В соответственно.
  `level` хранится как PostgreSQL enum `critical / warning`; `code` — текст,
  чтобы новые коды валидации не требовали миграции enum.
- `summary` — рекомендация ИИ; `secretary_decision` — отдельное решение человека.
- Удаление заявки удаляет диагнозы, строки и замечания через ON DELETE CASCADE.
  Удаление отдельного диагноза сбрасывает `diagnosis_id` у строк через SET NULL.
  Связь строки с диагнозом той же заявки предполагается при записи; составного FK нет.
- Время хранится с часовым поясом; `created_at` и `updated_at` заполняются БД,
  `updated_at` обновляется при UPDATE через SQLAlchemy (без триггера для произвольного SQL).

## Парсер Excel

`app.services.excel_parser.parse_excel(source)` принимает `bytes` или открытый
бинарный файловый объект и возвращает `ParseResult` из `app/schemas/parsing.py`.
Используются pandas и openpyxl, читается только первый лист. БД и настройки
подключения для парсинга не нужны. Содержимое ячеек не логируется и не включается
в сообщения ошибок. Парсер не выполняет медицинский анализ и проверки бизнес-правил.

Словарь синонимов и глубина поиска заголовков находятся в `app/column_synonyms.py`.

Принятые соглашения парсинга:

- Среди первых 10 строк выбирается строка с максимальным числом разных распознанных
  полей; при равенстве выбирается первая. Одного известного поля достаточно.
  Если совпадений нет (в том числе на пустом листе), возвращается `HEADER_NOT_FOUND`,
  пустой `items` и все пять полей в `missing_columns`.
- `column_mapping` имеет вид `{исходный заголовок: каноническое поле}`. Исходные
  заголовки, включая пробелы и переносы, сохраняются в ключах. `unknown_columns`
  содержит исходные непустые неизвестные заголовки; пустые заголовки игнорируются.
  `missing_columns` перечисляет отсутствующие канонические поля, без бизнес-валидации.
- При нескольких столбцах одного поля используется первый слева, остальные дают
  `DUPLICATE_COLUMN`. `ParseIssue.row` — номер строки Excel начиная с 1,
  `ParseIssue.column` — каноническое имя поля; для проблемы всего листа оба равны `None`.
- После заголовков обрабатываются все непустые строки первого листа; пустота
  проверяется по всем столбцам, включая неизвестные. Исходные номера строк сохраняются.
- `quantity` и `amount` имеют тип `Decimal`, без округления и проверки знака или
  целочисленности. В JSON Pydantic сериализует их строками для сохранения точности.
  Запятая или точка означает десятичный разделитель; пробельные символы убираются.
  Символ валюты разрешён перед числом или после него, `руб.`/`руб` — после числа.
  Строки одновременно с точкой и запятой не угадываются и дают `INVALID_NUMBER`.
- Отсутствующие ячейки и строки из пробелов становятся `None` без ошибки. Неразобранное
  непустое число становится `None` с `INVALID_NUMBER`; остальные ячейки сохраняются.
  Текстовые `NA`, `NULL` и подобные обозначения не считаются пустыми автоматически.
- Битый файл, другой формат или книга без листов вызывают `ExcelParseError`
  с русским сообщением без исходных технических подробностей.

## Валидация

`app.services.validator.validate_file` проверяет расширение `.xlsx` и размер файла,
а `validate_parse_result` проверяет обязательные поля и предупреждения по строкам.
Лимит размера задаётся `MAX_EXCEL_SIZE_BYTES` и по умолчанию равен 10 МБ.
Предупреждения не делают заявку недействительной; `ValidationReport.is_valid` становится
`False` только при наличии критических проблем. Несколько диагнозов допустимы и дают
одно информационное предупреждение.

## Принятые допущения

- PostgreSQL 16 и синхронный SQLAlchemy с драйвером psycopg 3; Docker использует Python 3.11.
- `GET /health` проверяет процесс API, без обращения к БД, и возвращает HTTP 200:
  `{"status":"ok","disclaimer":"Анализ носит рекомендательный характер. Решение принимает человек."}`.
- Дисклеймер включён и в технический ответ согласно требованию `AGENTS.md`.
- Правила анализа и LLM-адаптер пока не определены; `analysis` и `traffic_light`
  содержат заглушки. Парсер, валидатор и модели хранения реализованы.
- Пример пароля предназначен только для локальной разработки; `.env` исключён из Git
  и контекста сборки. Данные PostgreSQL сохраняются в именованном томе.
- Диапазоны зависимостей заданы в `pyproject.toml`; lock-файл пока не используется.
