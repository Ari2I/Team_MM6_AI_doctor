# Врач — тестовый frontend реального API

React 19 + TypeScript + Vite. Требуется Node.js 22.12+ (или 24 LTS) и npm.
Из корня репозитория:

```sh
cd frontend
npm ci
npm run dev
```

По умолчанию запросы относительные: Vite проксирует `/applications` и `/health`
на `http://127.0.0.1:8000`, сохраняя путь. API должен быть запущен отдельно.
Список заявок не запрашивается. Сохранённую карточку можно открыть через
`?application={id}`.

`VITE_API_URL` — базовый URL API без завершающего слеша, по умолчанию пустая
строка. Например, для отдельного сервера задайте `VITE_API_URL=http://localhost:8000`
в локальном окружении Vite. Это публичная настройка времени сборки, секреты в неё
помещать нельзя. При отдельном origin backend должен разрешать CORS с credentials;
предпочтительно использовать прокси на том же origin. После смены переменной
нужно перезапустить Vite или пересобрать статику.

## Контракт

Источник: `app/schemas/application_api.py`. Runtime-проверка находится в
`src/contract.ts`: проверяются вложенные объекты, массивы, перечисления и типы
значений; неизвестные дополнительные поля допускаются. Некорректный ответ
показывает сообщение о неподдерживаемом формате.

| Запрос | Данные |
| --- | --- |
| POST /applications | multipart: `file`, необязательные повторяемые `diagnoses` |
| GET /applications/{id} | ApplicationCard |
| GET /applications/{id}/report.xlsx | Отчёт Excel; доступен после анализа |

Загрузка возвращает ApplicationCard, включая `application`, `disclaimer`,
`diagnoses[]`, `items[].checks[]`, `issues[]`. Ошибки читаются из `errors[]`,
включая строку и столбец. Сетевая ошибка и 401 показываются отдельно, в том числе
при скачивании отчёта. Экрана входа здесь нет: при 401 требуется вход через
инфраструктуру окружения. Cookies передаются с запросами; токенов в коде нет.

Дополнительные диагнозы вводятся по одному на строку; пустые строки пропускаются.
Читается первый лист XLSX, выбор листа/столбцов API не поддерживает.
Проверки показаны непосредственно под своей позицией, без пересчёта категорий.
Категории A/B/V отображаются как А/Б/В, null — «не определена».

Допущения отображения: `category_shares` — готовые проценты (0–100),
`*_amount` и `total_amount` — суммы из backend; отсутствующее значение не
подменяется нулём. Валюта API не задана, поэтому суммы показываются без символа
валюты. null-комментарий/источник/версия обозначают отсутствие данных;
медицинские пояснения не дописываются. Справочник явно помечен демонстрационным.
Резюме, предупреждения и дисклеймер выводятся как получены от backend.

## Сборка и nginx

```sh
npm ci
npm run build
npm test
```

Проверяется TypeScript, статика создаётся в `dist/`.
`npm test` проверяет runtime-контракт на `sample_api_response.json`, multipart,
пути запросов, ошибки и 401 без запуска backend и внешней сети.
Dockerfile многоступенчатый: Node 22 для сборки, nginx для статики.
Из корня репозитория:

```sh
docker build -t vrach-frontend ./frontend
docker run --rm --network proekt_prac_2_default -p 8080:80 vrach-frontend
```

Имя сети — пример стандартной сети Compose; замените на фактическое.
nginx должен находиться в одной Docker-сети с сервисом `api:8000`.
Корневой Compose не изменён, frontend в него автоматически не добавляется.
`nginx.conf` раздаёт SPA с fallback на index.html, проксирует `/applications`
и `/health` без изменения пути, ограничивает тело 10m и задаёт таймауты 300s.
При необходимости внешний адрес API задаётся при сборке через
`--build-arg VITE_API_URL=https://backend.example.org`.

Frontend не добавляет вход в систему, polling, HTML-отчёт, цитаты или модельный
режим: таких возможностей текущий контракт не предоставляет. Правила светофора,
справочник, БД и анализ остаются на backend.
