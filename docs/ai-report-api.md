# Сохранённый AI-отчёт

`GET /applications/{application_id}/ai-report` читает последний сохранённый
AI-результат заявки. Запрос не выполняет анализ, не загружает источники и не
вызывает GigaChat/Embeddings. Текущие `ApplicationCard` и Excel не меняются.
Маршрут защищён общим Basic Auth nginx так же, как карточка заявки.

Это контракт backend. Подключение сетевого фасада и экран frontend — следующие
этапы; пока результат сохраняется только внутренним сервисом, публичного POST нет.

## Ответ 200: ai-report.1

| Поле | Тип и смысл |
| --- | --- |
| `schema_version` | `"ai-report.1"` |
| `application_id` | UUID заявки |
| `saved_at` | ISO 8601, время сохранения с часовым поясом |
| `backend_revision`, `ai_revision` | Полные SHA исходников сборки, по 40 hex-символов |
| `completeness` | `COMPLETE` или `PARTIAL` из IntegrationResult; COMPLETE не означает отсутствие ошибок пар |
| `human_report` | Неизменённый `human-report.1` из библиотечного результата |
| `checks` | Отдельные проверки и привязка каждой строки human_report к сохранённой паре |

`human_report` содержит `schema_version`, `title`, `notice`, `summary`,
`recommendation_note`, `review_note`, `items`, `costs` и
`purchases_without_amount_count`. У строки `items`: `number`, `name`, `diagnosis`,
`category`, `evidence`, `comment`, массивы `established`, `uncertain`, `questions`,
`actions`, `sources`. Источники содержат `number`, `title`, `version`, `location`,
`quote`, `url`, `copy_url`. Суммы `costs[].amount` — десятичные строки, валюта —
`costs[].currency`. Подробные типы публикуются в Pydantic-схемах backend.

Каждый элемент `checks`:

| Поле | Тип и смысл |
| --- | --- |
| `number` | Номер соответствующей строки human_report.items, начиная с 1 |
| `item_id`, `diagnosis_id` | UUID позиции и диагноза из текущей заявки |
| `row_number` | Номер строки исходного XLSX |
| `backend_rule` | PairCheck: `category`, `source`, `reference_version`, `comment`, `needs_review`, `review_reason` |
| `ai_rule_category` | Категория утверждённого корпуса библиотеки, А/Б/В/null; не SQL-категория |
| `ai_proposed_category` | Предложение ML-2, А/Б/В/null |
| `classification_basis` | Библиотечное APPROVED_RULE/ML2_PROPOSAL/CONFLICT/NONE; null для необработанной пары |
| `conflict` | true при библиотечном конфликте либо расхождении SQL-категории с непустой AI-категорией |
| `processed` | Есть ли пара в pairs; false для unprocessed_pairs |
| `generation_mode` | OFFLINE/MODEL/FALLBACK; null для необработанной пары |
| `form_status` | MATCH/MISMATCH/UNKNOWN; null для необработанной пары |
| `reasons` | Причины библиотеки; это отдельный справочник, не backend ReviewReason |

Frontend связывает строки по `number`, а сущности — по UUID, не по названиям.
Имена препаратов и диагнозов могут повторяться. SQL-категория остаётся основной,
AI-категории показываются отдельно. Библиотечный human_report не переписывается:
его строка может содержать AI-категорию, отличающуюся от SQL. Не выдавать её за
окончательную backend-категорию. Все предложения AI требуют ручной проверки.
`FORM_MISMATCH` — отдельное предупреждение и действие по сверке из human_report,
не замена категории и не проверка схемы приёма. Суммы не складывать повторно по
строкам диагнозов; источник денежных итогов отчёта — `human_report.costs`.

Для PARTIAL список checks включает и необработанные пары с их причинами.
При COMPLETE всё равно проверять reasons, generation_mode и предупреждения.
Полный/частичный fallback — сохранённый результат и ответ 200, а не доказательство
успешного обращения к модели. Если worker не вернул результат, новый отчёт не
создаётся. Правила его запуска и обработки таймаута реализуются следующим этапом.

## Хранение и согласованность

Таблица `application_ai_results`: `application_id` — первичный ключ и внешний
ключ applications с ON DELETE CASCADE; `result` JSONB — полный проверенный
IntegrationResult со снимком оснований; `checks` JSONB — снимок привязок и SQL-правил;
`backend_revision`, `ai_revision` — SHA; `saved_at` — время последнего сохранения.

Запись выполняется внутренним сервисом в транзакции вызывающего кода. Перед ней
полный результат валидируется публичной моделью AI лениво, проверяются ID и точное
покрытие пар заявки, исходные покупки/диагнозы и версия текущего входного контракта.
Категории SQL вычисляются из активного backend-справочника на момент сохранения,
не копируются из потенциально обогащённых AI item_checks. Для воспроизводимого
чтения снимок правил сохраняется вместе с отчётом. Запись не меняет item_checks,
статус, светофор и Excel.

Успешное повторное сохранение атомарно заменяет последний результат и его снимок;
история анализов в этом шаге не вводится. Невалидная или относящаяся к другой заявке
запись отклоняется без замены прежнего результата. Для конкурентного сохранения
сервис блокирует строку заявки до конца транзакции. Будущий повторный анализ должен
использовать тот же порядок блокировок; удаление устаревшего результата при правке
заявки входит в интеграцию запуска анализа, не в GET.

Чтение сохранённого JSON и схемы ответа не импортируют llm_rag/SDK. Библиотечная
валидация выполняется только при записи; повторный просмотр не требует наличия
реестра, кэша, сети или установленной AI-библиотеки. Полный IntegrationResult через
этот маршрут не выдаётся: исходная заявка и технические детали остаются на сервере.
Новая таблица создаётся только миграцией Alembic.

## Ошибки

Единый формат `{ "errors": [{ "level", "code", "message", "row", "column" }] }`.

- 404, `not_found`: «Заявка не найдена.»
- 409, `report_not_ready`: «Сохранённый ИИ-отчёт пока недоступен.» Наличие и состояние
  отчёта не определяются режимом AI или текущим статусом заявки.
- 422, `invalid_request`: недопустимый UUID, стандартный обработчик backend.
- 500, `http_error`: сохранённый результат невозможно прочитать; безопасное общее
  сообщение без содержимого JSON или ошибки валидатора.
- 401 на nginx: требуется Basic Auth, существующее поведение защиты.

Новые коды ReviewReason не вводятся. Значения ячеек, диагнозы, цитаты и ошибки
библиотечной валидации не пишутся в логи/ошибки. Ключи и реальные данные не входят
в примеры, Git или Docker-образ.

## Приёмка этого шага

Проверить PostgreSQL roundtrip полного/частичного/fallback-результата, повторную
запись, сохранность снимка при смене активного справочника, каскадное удаление,
отклонение чужих ID/пар и невозможность повредить прежнюю запись невалидным входом.
GET повторяется без сети и AI-библиотеки; ответы 404/409/422 безопасны.
Карточка/Excel и запрет сети локальных режимов сохраняются. Реальный фасад,
поддержка age_group новой AI-ревизии и frontend в этом шаге не подключаются.

### Команды контейнерной проверки

В прежнем терминале с функцией dc_rag и экспортированными настройками запуска:

```bash
export API_BUILD_TARGET=ai-offline AI_MODE=template
dc_rag up --build --force-recreate -d --wait --wait-timeout 180 api web
dc_rag cp sample_api_response.json api:/app/sample_api_response.json
dc_rag exec -T api alembic upgrade head
dc_rag exec -T api alembic check
dc_rag exec -T api python - <<'PY'
import os
import pytest
for key in ('DOCS_ENABLED', 'LIST_ENDPOINT_ENABLED', 'ENABLE_API_DOCS'):
    os.environ.pop(key, None)
os.environ['RUN_POSTGRES_TESTS'] = '1'
os.environ['ENABLE_APPLICATION_LIST'] = 'true'
raise SystemExit(pytest.main([
    '-q', '-rs', '--tb=no',
    'tests/test_ai_reports.py',
    'tests/test_ai_reports_postgres.py',
    'tests/test_ai_isolation.py',
    'tests/test_integration_mapping.py',
]))
PY
```

Без настроенного RAG-стека использовать функцию dc из предыдущей инструкции;
новым тестам реальные RAG-данные не нужны. Копирование sample_api_response.json —
обход прежнего отсутствия тестовой фикстуры в Dockerfile, сам образ в этом шаге
не изменяется. Тесты используют синтетические заявки в откатываемых транзакциях;
публичный маршрут сохранения результата не добавляется.

Для существующих заявок без AI-результата GET нового маршрута сейчас возвращает
409 — это ожидаемо, пока сетевой worker не подключён. Корректный ответ 200 и
повторное чтение проверяются синтетическими PostgreSQL/HTTP-тестами выше.
