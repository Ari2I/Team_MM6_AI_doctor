# Протокол worker целой заявки

Протокол внутренний, не HTTP API и не формат запроса к GigaChat. Новые
`IntegrationWorkerClient` и `app.services.integration_worker` подключены к загрузке
только в network. Попарный `ai_worker` и его протокол сохраняются для локальных режимов.

## Запрос через stdin

Один JSON `integration-worker-request.1` на один процесс:

- `schema_version`: `integration-worker-request.1`;
- `request_id`: UUID сохранённой заявки;
- `mode`: template/offline/network;
- `timeout_seconds`: положительный конечный бюджет в секундах;
- `payload`: проверенный `integration-request.1`, включая purchases/diagnoses/links.

Ключи, access token, CA-файлы, произвольные настройки SDK и отключение TLS в
протокол не входят. Секреты остаются в окружении запускаемого процесса. Запрос
не является логом: содержимое stdin/результата не печатается и не пишется в файлы.

Перед запуском клиент валидирует подготовленную заявку. Известная возрастная группа
передаётся каждому диагнозу в conditions.age_group=adult|child; age_years остаётся
неизвестным. Отсутствующая группа не подменяется значением по умолчанию.
В template/offline клиент не запускает процесс и не импортирует библиотеку.
Если worker запущен напрямую в локальном режиме, он также пропускает обработку
до импортов AI и создания провайдеров.

## Ответ через stdout

Ровно один JSON `integration-worker-response.1` и перевод строки. Поля:

- `schema_version`: обязательная версия integration-worker-response.1;
- `request_id`: тот же UUID; null допустим только в ответе об ошибке разбора входа;
- `outcome`: result/error/skipped;
- `result`: полный `IntegrationResult` либо null;
- `error`: существующий код ReviewReason либо null.

Допустимые комбинации:

| outcome | result | error |
| --- | --- | --- |
| result | Полный валидный результат, включая PARTIAL/fallback библиотеки | null |
| error | null | AI_INPUT_INCOMPLETE / AI_UNAVAILABLE / AI_TIMEOUT / AI_INVALID_RESPONSE |
| skipped | null | null |

`skipped` — внутренняя команда оставить текущий template/offline-путь; это не
запись об успешном сетевом анализе. Клиент network не принимает skipped от worker.
Дополнительные поля/версии, неизвестные коды, неправильные сочетания полей и
несовпадающий UUID отклоняются.
Отсутствующая версия на входе/выходе также отклоняется; значения по умолчанию
в Python-моделях нужны только при создании сообщения перед сериализацией.

Ответ result проверяется публичной моделью библиотеки и внутри worker, и в
родительском процессе. Исходный request должен совпадать с отправленным, а
покрытие пар, суммы, отчёт и снимок проверяет IntegrationResult. Повреждённый JSON,
посторонний stdout и неверный результат дают AI_INVALID_RESPONSE, без публикации
ошибки валидатора. Валидный PARTIAL принимается полностью, не подменяется общим
fallback только из-за неполноты.

## Ошибки и жизненный цикл

- Ошибка подготовленного входа — AI_INPUT_INCOMPLETE; отсутствующая библиотека —
  AI_UNAVAILABLE.
- TimeoutError worker или превышение внешнего бюджета — AI_TIMEOUT.
- Сбой запуска, аварийное завершение/ненулевой exit code — AI_UNAVAILABLE.
- Неправильная оболочка или результат — AI_INVALID_RESPONSE.
- Служебные исключения, SDK-ответы, stdout/stderr стороннего кода не выдаются.
  Worker отключает logging и перенаправляет stdout/stderr Python и файловые
  дескрипторы на /dev/null на время разбора и обработки; на выходе только протокол.
- Клиент использует subprocess.run: при таймауте дочерний worker убивается и
  дожидается завершения. Любой частичный stdout при timeout/crash отбрасывается.
  Сохранить можно только полностью возвращённый и проверенный IntegrationResult.

Используется уже существующий AI_APPLICATION_TIMEOUT_SECONDS, новый бюджет не
вводится. Бюджет включает подготовительную валидацию и ожидание worker; его остаток
передаётся в IntegrationOptions.deadline_seconds. Подбор бюджетов отложен по плану;
внутренний дедлайн не обещает доставку частичного результата до внешнего таймаута.

## Фасад и ограничения этого шага

В network worker вызывает публичный analyze_request() с явным
verify_ssl_certs=True и IntegrationOptions. Импорт фасада/SDK происходит только
в этом пути. При загрузке проверенный результат направляется в save_ai_result
и фиксируется вместе с карточкой. Нужны метаданные SHA сборки; детали и команды
проверки: [оркестрация загрузки](ai-upload-orchestration.md).
Поддержка age_group обновлена на AI-ревизию 8836cdb.

Тесты вызывают подменённый фасад и синтетические процессы под запретом сокетов/DNS;
реальная сеть, ключи, сертификаты и рабочие данные здесь не используются. Проверить
валидный полный/частичный результат, изменение request/ID, некорректный протокол,
исключения, утечку вывода, аварийное завершение и реальное завершение процесса при
таймауте. Импорт API и локальные режимы должны работать без llm_rag/SDK.

## Проверка в существующем контейнерном стеке

В том же терминале с функцией dc_rag и ранее заданными настройками:

```bash
export API_BUILD_TARGET=ai-offline AI_MODE=template AI_LIVE_SOURCES=false
dc_rag up --build --force-recreate -d --wait --wait-timeout 180 api web
dc_rag exec -T api pytest -q -ra --tb=no \
  tests/test_integration_worker.py \
  tests/test_ai_isolation.py \
  tests/test_tls_policy.py
```

Для этих тестов не нужны PostgreSQL-миграции, свежий RAG-кэш, ключ или CA.
GigaChat/Embeddings не вызываются: фасад и SDK подменены, дочерние процессы
проверяют только протокол/ошибки. Изменения API, БД, Dockerfile и зависимостей
в этом шаге не выполняются. Если стек запускается обычной dc без RAG override,
можно использовать её: важен target ai-offline, чтобы выполнить библиотечную
валидацию, а режим самого API остаётся template.
