# AI-отчёт при загрузке заявки

POST /applications сохраняет разобранную заявку и вызывает существующий анализ.
В AI_MODE=template/offline работает прежний попарный путь. В AI_MODE=network
после SQL-сопоставления МНН вызывается один IntegrationWorkerClient на всю заявку:
IntegrationRequest → worker → analyze_request() → IntegrationResult.
Прежний попарный network-worker при загрузке больше не запускается.

Группа adult/child передаётся каждому диагнозу; точный возраст не подставляется.
Покупки и связи имеют сохранённые UUID. Передача полного запроса дочернему процессу
не означает разрешения отправлять эти поля в GigaChat: фильтрация провайдера
сохраняется в библиотеке. Содержимое заявки, stdout/stderr и ошибки валидатора
не пишутся в логи и ответы об ошибках.

## Запись и fallback

- Перед пересчётом удаляется предыдущий AI-снимок, в том числе при переходе на
  template/offline. Неудачная новая попытка не выдаёт старый отчёт за новый.
- Полностью полученный и валидный IntegrationResult сохраняется целиком: COMPLETE,
  PARTIAL с unprocessed_pairs, результат с библиотечным FALLBACK. HTTP 200/201 и
  наличие AI-отчёта сами по себе не подтверждают успешные вызовы модели.
- При таймауте, недоступности, неправильном результате или ошибке сохранения
  сохраняется детерминированная карточка с needs_review и существующим кодом
  причины AI_*. Без результата GET /applications/{id}/ai-report возвращает 409.
- Запись снимка выполняется в savepoint; ошибка откатывает только эту запись.
  Проверки, агрегаты и AI-отчёт фиксируются одним общим commit анализа. Ошибка
  всего анализа откатывает и новый AI-отчёт, затем действует прежний статус error.
- Блокируется строка заявки до удаления/замены её снимка. При записи используется
  тот же SQL-снимок правил, по которому строится карточка, даже если активный
  справочник был переключён за время работы worker.

GET карточки, Excel и AI-отчёта читают сохранённые данные, не повторяют worker.
AI_MODE по умолчанию остаётся template. Бюджеты, TLS=True и принудительное
завершение worker при таймауте не меняются.

## Проекция в прежнюю карточку

SQL-категория, источник и версия сохраняют приоритет. AI-категория без SQL-правила
показывается только как предложение с needs_review и AI_PRELIMINARY. Библиотечный
конфликт не разрешается выбором лучшей категории; при расхождении с SQL остаётся
SQL-категория и предупреждение. Сбой источника/модели не создаёт новую категорию.
Полные AI-основания, цитаты и human_report находятся в отдельном сохранённом отчёте;
произвольный модельный текст не копируется в старую карточку.

FORM_MISMATCH добавляет отдельное предупреждение о сверке формы/концентрации,
не меняет категорию. Расчёт долей/светофора и однократный учёт суммы позиции
остаются в backend. SQL-МНН сохраняется; если его нет, карточка получает единственное
непротиворечивое inn позиции из валидного фасадного результата. Фасад не возвращает
числовой match_confidence, поэтому он остаётся null, не подставляется 1.0.
Новые backend-коды причин, API-поля и миграции не добавляются.

## Метаданные сборки

Для network нужны AI_BACKEND_REVISION и AI_LIBRARY_REVISION: полные SHA по 40
строчных hex-символов. Compose передаёт их в API; они сохраняются как
backend_revision/ai_revision. Это несекретные метаданные исходников собранного
образа. SHA не определяются автоматически и не подменяются фиктивным значением.
Если хотя бы один SHA отсутствует, worker не запускается, карточка получает
AI_UNAVAILABLE. Отсутствие этих настроек не мешает template/offline.

Перед будущей реальной сетевой приёмкой в чистом отслеживаемом дереве:

```bash
export AI_BACKEND_REVISION="$(git rev-parse HEAD)"
export AI_LIBRARY_REVISION=8836cdbd9a73b59949ac4acc58276cbe3bee4dad
```

После изменения кода метаданные обновить и пересобрать образ. Эти команды сами
не включают network. Ключ, scope, CA и постоянный RAG_DATA_DIR настраиваются и
проверяются отдельным следующим шагом; здесь реальная сеть не проверена.

## Проверка без GigaChat в существующем стеке

В прежнем терминале с dc_rag и настройками запуска:

```bash
export API_BUILD_TARGET=ai-offline AI_MODE=template AI_LIVE_SOURCES=false
dc_rag up --build --force-recreate -d --wait --wait-timeout 180 api web
dc_rag cp sample_api_response.json api:/app/sample_api_response.json
dc_rag exec -T api alembic upgrade head
dc_rag exec -T api alembic check
dc_rag exec -T api python - <<'PY'
import os
import pytest
for key in ('DOCS_ENABLED', 'LIST_ENDPOINT_ENABLED', 'ENABLE_API_DOCS'):
    os.environ.pop(key, None)
os.environ['RUN_POSTGRES_TESTS'] = '1'
os.environ['ENABLE_APPLICATION_LIST'] = 'true'
raise SystemExit(pytest.main(['-q', '-rs', '--tb=no']))
PY
```

tests/test_application_ai.py проверяет один вызов на заявку, группы, SQL-приоритет,
предложения/конфликты, PARTIAL/fallback, ошибки сохранения, отсутствие SHA и локальные
режимы под запретом сети. tests/test_application_ai_postgres.py проверяет настоящий
POST → JSONB → GET → повторный GET, Excel, удаление прежнего отчёта после отказа и
атомарность с карточкой. Worker в этих тестах подменён; GigaChat/Embeddings не
вызываются. В PostgreSQL-тестах запрет сокетов накладывается только на подменённый
фасад: сам HTTP-клиент и соединение с БД используют служебные сокеты.

После тестов в режиме template повторить прежние smoke и ручные четыре файла.
Для golden использовать сохранённые эталоны, не перезаписывать их:

```bash
.venv/bin/python scripts/compare_golden.py
```

Команда использует прежние WEB_URL/WEB_USER/WEB_PASSWORD, значений не печатает.
Нужен активный demo-v2 со справочником/названием, на котором снимались эталоны.
Реальный сетевой прогон и новый frontend эта проверка не заменяет.
